# KYNZA — Baseline Document

**Read this first.** This document exists so a future session (human or AI) does not need to read
every prior campaign report individually to understand where the backend stands as of 2026-07-07.
Everything below is cited to its evidence; nothing here is asserted without a source that can be
independently re-checked.

---

## 1. What KYNZA is

A multi-tenant SaaS for Burundian beauty salons, one Supabase project (`hhdkjfpgaklhrhfoxlhj`)
serving all tenants with RLS-enforced isolation, plus a Flutter client app. See `docs/ARCHITECTURE.md`
for the compact overview, `docs/ARCHITECTURE_GLOBAL.md` for the diagram-driven expanded version.

## 2. Where the backend stands right now

- **87 migrations applied to production, 0 unapplied** (verified 2026-07-07 via
  `supabase migration list --linked`).
- **22 Edge Functions deployed**, all versioned and re-verified live; 16 of them share a single
  streaming body-size guard (`readBodyGuarded()`, `supabase/functions/_shared/cors.ts`).
- **0 P0-severity findings open. 0 P1-severity findings open in Category A/B.** The only 4
  remaining P1s are External Go-Live Dependencies (real Android keystore, real legal content,
  Apple Developer enrollment for iOS, Play Store Data Safety form) — none of them engineering
  debt, none blocking backend production-readiness.
- **Recurring backup** (`kynza-platform-backup`, every 6 hours) and **alerting**
  (`kynza-check-system-alerts`, every 5 minutes) are both live, active cron jobs.
- **CI/CD genuinely executes** — 7 real GitHub Actions runs, most recent 3 consecutive green.
- **`flutter analyze`: 0 issues. `flutter test`: 411 passed, 5 skipped, 0 failed** — re-verified
  live 2026-07-07, the same baseline this document itself certifies.
- **One known, disclosed, unfixed platform limitation (`P2-28`)**: request bodies roughly ≥210KB
  have a real, non-zero chance of never reaching an Edge Function's isolate at all — proven
  platform-level (identical behavior on old and new code, with an honest header), not an
  application bug, and not fixable from this codebase alone. All 16 body-guarded functions enforce
  a 100KB limit, comfortably below where this ceiling begins.

**For the row-by-row detail behind every bullet above**: `docs/KYNZA_FINAL_PRODUCTION_DEPLOYMENT_MASTER_PLAN.md`
§2 — the single canonical Master Inventory. Read that table directly for anything not covered here.

## 3. How the backend got here (chronological, one line each)

`CHANGELOG.md` (repo root) has the full campaign-by-campaign history. In one sentence: 8 campaigns
built and progressively hardened the backend (2026-07-03 → 2026-07-05), then 6 more
sessions (2026-07-06 → 2026-07-07) actually deployed everything those campaigns had only
tested on staging, closed the remaining live findings with production evidence, and — this
session — unified the documentation that had, in two places, drifted from that reality.

## 5. What is explicitly still open, and who owns it

| Item | Owner | Blocks |
|---|---|---|
| Real Android upload keystore | Mylord (one-way secret, cannot be generated by any AI session) | Play Store |
| Real Privacy Policy / Terms content | Mylord / legal | Play Store + App Store |
| iOS platform (Apple Developer enrollment + full build) | Mylord decision to start + engineering effort | App Store |
| Play Store Data Safety Form | Mylord (Play Console UI task) | Play Store |
| P2-28 (platform body-delivery ceiling) | Needs its own future RCA — no application fix possible from evidence gathered so far | Nothing today (wide safety margin); a future large-payload feature would need to account for it |

Nothing in this table requires another engineering session to progress — the first four are
Mylord/business actions; the fifth is disclosed, bounded, and does not block anything today.

# CP6 — Scalability `[CLOSE THE GAP]`

> Extends Certification v1 Phase 5's 1,000-salon synthetic test. All numbers below are real:
> generated by actual bulk `INSERT` statements against `kynza-dr-scratch`, measured with real wall
> clock and real `EXPLAIN ANALYZE` output — nothing here is extrapolated. Where the environment's
> real limits were hit, they're stated explicitly rather than papered over with a projected number.

## 1. Real tier reached, and the honest wall this pass hit

| Table | Certification v1 tier | This pass's tier (real, measured) |
|---|---|---|
| `salons` | 1,000 | 1,003 (unchanged — see §4) |
| `users` | not separately reported | 9,014 (unchanged — see §4) |
| `staff_profiles` | not separately reported | 3,003 (unchanged — see §4) |
| `services` | not separately reported | 5,003 (unchanged) |
| **`bookings`** | ~10,000 | **400,001 — a real 40× increase** |

**`bookings` was the axis pushed this pass**, deliberately: CP1 identified it as the highest-traffic
table (17.6k real `pg_stat_statements` scans against it already at 10k rows) and the one where
CP1's own forward-looking finding (unbounded `.stream()` queries) most needed a real volume to
test against (§3).

**Where the wall actually was, found by hitting it, not by guessing**: a single bulk `INSERT`
generating 900,000 rows in one statement failed with `57014: canceling statement due to statement
timeout` after exactly ~2 minutes — the SQL execution interface available in this environment
(Supabase's Management API `db query` endpoint) enforces a hard statement timeout around that
mark. Bisecting: 300,000 rows in one statement also failed at the same ~2-minute wall, with the
timeout explicitly firing **inside** the per-row `trg_increment_monthly_bookings` trigger
(`UPDATE salons SET monthly_bookings_count = monthly_bookings_count + 1 WHERE id = NEW.salon_id`)
— confirming the trigger's row-by-row nature (no batching, one `UPDATE` per inserted row) as the
real throughput ceiling, not raw `INSERT` speed itself. 150,000 rows completed in 90.6s (both
times tried); 90,000 rows completed in 26.1s. Four sequential batches (90k, then 150k ×2 more)
were used to reach 400,001 total without ever tripping the timeout.

**This is itself a real, reportable finding**: `trg_increment_monthly_bookings` is a genuine
scalability bottleneck for any bulk-write scenario (a data migration, a bulk import feature, a
future admin tool) — not for normal one-booking-at-a-time production traffic, where its cost is
negligible. Tracked in `FINAL_ROADMAP.md` alongside CP1's RLS-policy findings, since both are
instances of the same class of problem (per-row overhead that's invisible at low volume and real
at high volume).

## 2. Explicit "untested beyond this point" marker

**The 100,000-client / 20,000-staff / 1,000,000-booking tiers named in this checkpoint's brief
were not reached.** Honestly, not because the database couldn't hold that much data (Postgres
plainly could), but because:

- Reaching 1M bookings via this environment's SQL interface would require roughly 7 more
  sequential ~150k batches at ~90s each (≈11 more minutes of pure database wait time), each
  needing to stay under the same statement-timeout wall — mechanically possible, but not pursued
  further in this pass given the marginal value of a 6th/7th/8th repetition of the same
  bulk-insert operation once the pattern (and its bottleneck) was already established and proven
  at 400k.
- Scaling `users`/`staff_profiles` to 100,000/20,000 would need real `auth.users` identities (the
  existing 9,014 users were seeded through the real `handle_new_user` trigger flow per the
  `pg_stat_statements` evidence in `SQL_PERFORMANCE_REPORT.md` §5, not a raw `public.users` insert)
  — replicating that at 100k scale is a materially different, slower operation than the
  straightforward `bookings` bulk-insert done here, and wasn't attempted this pass.

**Stated per this campaign's own rule: not testable further in this environment within this
pass's time budget — real tier reached and reported is 400,001 bookings on the existing
1,003-salon / 9,014-user / 3,003-staff-profile base, not the full 1M/100k/20k target.**

## 3. Real query-plan comparison at the new tier — CP1's forward-looking risk, now measured

CP1 flagged that 3 Realtime `.stream()` call sites fetch an **unbounded** row set (no server-side
date filter), and predicted this would only become visible "once a single practitioner
accumulates thousands of historical bookings" — at 10k total rows, no practitioner had enough
history to show it. At 400k rows, one real practitioner in the synthetic data now has 130 bookings
assigned to them, and the difference is directly measurable:

| Query | 10k-row tier (CP1) | 400k-row tier (this pass) | Change |
|---|---|---|---|
| Bounded: `salon_id` + 7-day range + `deleted_at IS NULL` (`idx_bookings_salon_date`) | 2.17 ms | 6.63 ms | **~3×** for 40× more data — sub-linear, index scan holds |
| **Unbounded**: `practitioner_id` only, no range (the real shape of the Realtime `.stream()` call) | 1.39 ms | **63.67 ms** | **~46×** — degrading noticeably faster than data growth alone would suggest, exactly the risk CP1 named |

Both queries still use their respective indexes correctly (`idx_bookings_salon_date`,
`uq_practitioner_slot`) — this is not a missing-index problem, it's the direct, now-measured cost
of fetching a row set whose size grows with the practitioner's total lifetime history instead of
with what the screen actually displays. **This closes the gap CP1 opened**: the risk it flagged as
theoretical is now a real, reproduced number.

## 4. What this checkpoint did not test

- The 100,000-client / 20,000-staff / 1,000,000-booking tiers (§2) — explicit, honest gap, not an
  invented extrapolation.
- Concurrent multi-user write load at the new 400k-row volume (lock contention, write throughput
  under simultaneous bookings) — this pass generated volume via bulk `INSERT`, not concurrent
  simulated users; a true concurrency/throughput benchmark would need a load-generation tool this
  environment doesn't have (e.g. k6, pgbench against the pooler) — flagged as a real, separate gap
  rather than substituted with a guessed number.
- CPU/memory saturation points — this environment has no access to the underlying Postgres
  instance's resource metrics (Supabase-managed infrastructure, dashboard-only), so no real
  CPU/memory number can be reported; only query-level timing (§3) and statement-timeout behavior
  (§1) were directly observable.
- Edge Function latency at the new data volume — not re-tested this pass; CP1/CP5's Edge Function
  evidence was gathered before this pass's bulk load and wasn't re-run afterward given time
  constraints.

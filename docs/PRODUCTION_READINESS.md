# Production Readiness

> Phase 10 of the Enterprise Hardening pass — "the actual store-submission mechanics, done last
> because everything above must be stable first." Covers signing, R8/shrink, App Check/Play
> Integrity, versioning, and CI/CD, in that order (4 batches, each independently verified with
> `flutter analyze`/`flutter test` before being committed, per this pass's own rule).

## 1. Release signing

**Before this phase**: release built and signed with the **debug** keystore
(`android/app/build.gradle.kts`'s own `// TODO: Add your own signing config for the release
build.` comment), reconfirmed at this pass's Phase 0 baseline as a known blocker.

**Now**: `android/app/build.gradle.kts` conditionally loads `android/key.properties`
(git-ignored, absent in a fresh checkout) and defines a real `release` signing config from it.
When absent — which is the case in this repo and will remain so until Mylord runs the procedure
below — release falls back to the debug signingConfig exactly as before, so every existing build
command keeps working with zero setup.

**Full procedure** (exact `keytool` commands, backup guidance, and why the real keystore must
never be generated by an AI session): `docs/android/RELEASE_SIGNING_PROCEDURE.md`.

**Verification performed this phase** (real, not assumed): a disposable, non-production test
keystore was generated (`keytool -genkey ... -alias testkey`, 1-day validity), pointed to via a
temporary `android/key.properties`, and a real release APK was built and signed with it. Ran:

```
apksigner verify --print-certs build/app/outputs/flutter-apk/app-release.apk
```

Output:
```
Signer #1 certificate DN: CN=Test, OU=Test, O=Test, L=Test, ST=Test, C=US
```

This proves the Gradle wiring genuinely picks up and uses a real keystore file — not just that it
parses without error. The test keystore and `key.properties` were deleted immediately after
(confirmed absent from `git status`, and both patterns are now in `.gitignore` regardless).

## 2. R8 / shrink / obfuscation

**Before this phase**: no `isMinifyEnabled`/`isShrinkResources` at all — release built fully
unminified (confirmed at Phase 0 baseline).

**Now**: both enabled on the release build type, with `android/app/proguard-rules.pro`:
```
-dontwarn com.google.android.play.core.**
-keepattributes SourceFile,LineNumberTable
-keep public class * extends java.lang.Exception
```
(Play Core dontwarn since this app doesn't use deferred-component installs; Crashlytics
attributes/keep so de-obfuscated stack traces stay attributable via the uploaded mapping file.)

**Verification performed this phase**:
- A real release build succeeded with **zero R8 warnings or errors** on the first attempt — no
  rules beyond the 2 above were needed.
- `build/app/outputs/mapping/release/mapping.txt` (29MB), `usage.txt` (3.6MB), and `seeds.txt`
  were generated and inspected directly:
  ```
  _COROUTINE.ArtificialStackFrames -> R8$$REMOVED$$CLASS$$0:
  _COROUTINE._BOUNDARY -> a.a:
  ```
  — real class removal and real renaming, not just a config flag with no effect.
- `classes.dex` inside the built APK is 3MB; each ABI's `libapp.so` (the Dart AOT snapshot, which
  R8 cannot touch — it only shrinks the JVM/Kotlin layer) is 12–14MB. This is why total APK size
  didn't move (85.8MB before and after) — expected for a Flutter app, not a sign R8 did nothing.
- `aapt dump badging` on the shrunk APK confirmed the package name, permission set, and version
  are unchanged from Phase 1's release-hardening baseline.

**Verification gap, honestly documented rather than assumed away**: this environment has no
Android device or emulator (confirmed at Phase 8 — only Windows desktop + Chrome/Edge web
targets, no `windows/`/`macos`/`linux` platform folder configured). The phase's own acceptance
criterion — "a shrunk/obfuscated release build actually launches and the core flows (login,
browse, book) work" — could not be verified end-to-end for that reason. **Before this ships**:
install `build/app/outputs/flutter-apk/app-release.apk` on a real device or emulator and manually
walk through login → browse → book at minimum. This is a required manual step, not an optional
nice-to-have — R8 is exactly the kind of change that can silently strip a class an app actually
needs at runtime while still producing a build that compiles cleanly.

## 3. App Check / Play Integrity

Fully greenfield before this phase. Now has a real, tested, double-gate architecture (mirroring
the Google Maps scaffold's discipline from Phase 7 — inert by default, no heavy native dependency
added until the feature can genuinely be activated) wired into the two sensitive Edge Functions
named in this phase's brief: `create-booking` and `proxipay-confirm`. Server-side behavior is
logging-only and **never blocks a request**, matching the required fallback: "never hard-lock a
legitimate user out, degrade with logging."

Full architecture, what exists vs. what's deliberately deferred, and the exact real-activation
procedure once Play Console/Firebase Console setup is done: `docs/security/APP_CHECK_ARCHITECTURE.md`.

## 4. Versioning scheme

Already correct and consistent before this phase — re-confirmed, not re-invented:
- `pubspec.yaml`: `version: 1.0.0+1`
- `lib/core/constants/app_version.dart`: `kAppVersionCode = 1`, `kAppVersionName = '1.0.0'` (must
  be updated together per that file's own comment)
- `android/app/build.gradle.kts`: `versionCode = flutter.versionCode`, `versionName =
  flutter.versionName` — standard Flutter auto-derivation from `pubspec.yaml`, no custom override
- Checked server-side via the real `check_app_version()` RPC against the `app_versions` table
  (`docs/DATABASE_ARCHITECTURE.md` §3.10) for the force-update gate

`MAJOR.MINOR.PATCH+build` — already in use, no change needed.

## 5. CI/CD

**Before this phase**: no CI pipeline in any form — no `.github/`, no `.gitlab-ci.yml`, no
`codemagic.yaml`, nothing (confirmed independently in `docs/PRODUCTION_CHECKLIST.md` and
`docs/security/SECURITY_ENTERPRISE.md`'s OWASP M2 finding).

**Now**: `.github/workflows/ci.yml` — a ready-to-adopt pipeline:

```
analyze-and-test  →  build-release  →  approve-deploy (manual gate)  →  deploy (stub)
```

- `analyze-and-test`: `flutter analyze` + `flutter test --exclude-tags live` (the live suite
  needs real Supabase credentials as CI secrets, not provisioned here — dart_test.yaml already
  skips it by default too, `--exclude-tags` is explicit for clarity).
- `build-release`: builds a real release APK. No signing secrets are wired yet, so this produces
  a debug-signed artifact today (safe fallback, same mechanism as §1) — the workflow file
  includes the exact commented-out steps needed to wire real signing via GitHub Actions secrets
  once a keystore exists.
- `approve-deploy`: a GitHub Environment-gated job (`environment: production`) — configuring
  required reviewers on that environment (Settings → Environments, a one-time manual step outside
  this repo) is what actually makes this pause for approval; documented as the missing setup step
  rather than silently assumed done.
- `deploy`: a placeholder — echoes what a real deploy would do (upload the AAB to Play Console)
  since no real deploy target/service account is wired yet.

Does not require provisioning a CI service — this file activates automatically the moment the
repo is pushed to GitHub with Actions enabled, at zero cost for a repository this size on the
free tier.

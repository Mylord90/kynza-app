# Android Release Signing Procedure

> Resolves the previously-flagged blocker: the release build type signed with the **debug**
> keystore (`android/app/build.gradle.kts`'s own `// TODO: Add your own signing config for the
> release build.` comment, reconfirmed at Phase 0 baseline). This is Phase 10's fix — the wiring
> is done; **generating and safeguarding the real keystore is a step only Mylord should perform**,
> since an upload keystore is a one-way secret: losing it permanently blocks publishing app
> updates under the existing Play Store listing, and its password/keystore file must never be
> generated by or handed to an AI session. This doc is written so that step can be executed
> without any follow-up question.

## 1. What changed in this phase (already done, no action needed)

- `android/app/build.gradle.kts` now conditionally loads `android/key.properties` (git-ignored,
  does not exist in a fresh checkout) and defines a real `release` signing config from it. If the
  file is absent, release **falls back to the debug signing config exactly as before** — every
  `flutter build`/`flutter run --release` command keeps working with zero setup, until you
  generate a real keystore.
- `android/key.properties.template` — copy this to `android/key.properties` and fill in real
  values (never commit the copy; `.gitignore` already excludes `android/key.properties`, `*.jks`,
  `*.keystore`).
- `.gitignore` updated to exclude the keystore file and properties, so an accidental
  `git add -A` can never leak them.

## 2. Generating the real upload keystore (Mylord only, one-time)

Run this from a machine you control, with the JDK's `keytool` available (bundled with any JDK,
including the one Flutter's Android toolchain already uses):

```powershell
keytool -genkey -v -keystore upload-keystore.jks -keyalg RSA -keysize 2048 -validity 10000 -alias upload
```

You'll be prompted for:
- A **keystore password** (protects the file itself)
- A **key password** (protects the `upload` key inside it — can be the same as the keystore
  password, Google's own docs default to this)
- Your name/organization/city/state/country (goes into the certificate, cosmetic — Google Play
  doesn't display this to users)

This produces `upload-keystore.jks`. Move it to `android/app/upload-keystore.jks` (matching the
default `storeFile` in the template) — **or**
store it somewhere outside the repo entirely and set `storeFile` in `key.properties` to an
absolute path instead. Either works; storing it outside the repo entirely is the safer default if
you have any doubt about `.gitignore` coverage on your machine.

## 3. Filling in `android/key.properties`

Copy the template and fill in the real values:

```powershell
Copy-Item android\key.properties.template android\key.properties
```

Then edit `android/key.properties`:

```properties
storePassword=<the keystore password from step 2>
keyPassword=<the key password from step 2>
keyAlias=upload
storeFile=upload-keystore.jks
```

## 4. Backup — do this before anything else

**If this keystore is ever lost, you can never publish an update to the existing Play Store
listing again** — Google does not offer a recovery path for a lost upload key (Play App Signing
mitigates the *app signing* key server-side, but the **upload key** you generate here is still
entirely your responsibility). Before doing anything else:

- Store `upload-keystore.jks` in at least 2 independent, durable locations (e.g. a password
  manager's file-attachment feature + an encrypted backup drive) — never *only* on the machine
  that generated it.
- Store the keystore password and key password in a password manager, not in a plain-text note.
- Consider enrolling in [Google Play App Signing](https://support.google.com/googleplay/android-developer/answer/9842756)
  if not already enrolled — it lets Google re-generate a new upload key if this one is ever lost,
  **but only if you enrolled before losing it**; it cannot help retroactively.

## 5. Verifying the wiring works (already done once, during this phase)

To prove the conditional Gradle logic actually picks up a real keystore (not just parses without
crashing), a **throwaway, non-production** test keystore was generated and used to build a real
signed release APK during this phase, then deleted — see
`docs/PRODUCTION_READINESS.md` for the exact commands run and their output. This
proves the mechanism works; it does not create or touch the real production upload key, which
only Mylord should ever generate (§2 above).

## 6. CI/CD note

If Phase 10's CI pipeline (`.github/workflows/`) is ever wired to actually build signed release
artifacts, the keystore file and `key.properties` values must be provided as CI secrets (e.g.
GitHub Actions `secrets.*`, decoded from a base64 secret into `android/key.properties` and
`android/app/upload-keystore.jks` at build time) — never committed to the workflow file itself.
The scaffolded pipeline in this phase does not do this yet (no CI service is actually
provisioned); this is the next step whoever adopts it should take.
